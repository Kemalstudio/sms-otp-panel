# SMS OTP Gateway — панель управления

SaaS-панель для управления шлюзом SMS OTP: проекты, привязанные телефоны-устройства,
API-ключи и логи одноразовых кодов.

Стек: Laravel 12 + Blade + Tailwind (Laravel Breeze, стек `blade`), SQLite.

## Быстрый старт

```bash
composer install
npm install && npm run build

cp .env.example .env
php artisan key:generate

docker compose up -d          # Postgres + Redis, см. «Продакшен» ниже
php artisan migrate --seed
php artisan serve
```

Для разового запуска без Docker сойдёт SQLite: поставьте `DB_CONNECTION=sqlite`
в `.env`. Для боя — нет, см. раздел про Postgres.

Демо-доступ из сидера: **demo@example.com / password**.
Сидер печатает в консоль сгенерированный API-ключ — в базе от него остаётся только sha256-хеш.

Файл `database/database.sqlite` создаётся автоматически (`composer install`
дергает соответствующий скрипт; при необходимости `touch database/database.sqlite`)
и используется, только если выбран `DB_CONNECTION=sqlite`.

## Безопасность

* **Полный API-ключ не хранится.** `ApiKey::generateFor()` генерирует `sk_live_<32 символа>`,
  в БД уходит `hash('sha256', $plain)` и первые 16 символов для отображения.
  Открытое значение возвращается один раз через flash-сессию и показывается в модалке.
* **Доступ к проектам — через политику, а не просто `auth`.** Группа `/projects/{project}`
  закрыта middleware `can:view,project` (`App\Policies\ProjectPolicy`), плюс `authorize()`
  в Form Request'ах. `->scopeBindings()` заставляет резолвить вложенные модели через
  связь проекта: чужой ключ отдаёт 404, а не отзывается.
* **Пароли** — стандартный хеш Breeze (bcrypt), не трогали.
* **Номера в логах маскируются** (`+993 XX XXX 4567`), полный номер показывается
  только по явному клику «показать». Оговорка: раскрытие сейчас клиентское, то есть
  полный номер всё же лежит в разметке страницы. Когда появится API шлюза, его нужно
  отдавать отдельным запросом с логированием доступа.

## Статус устройства

В таблице `devices` есть колонка `status`, но UI использует вычисленный статус:
устройство считается `active`, только если `last_seen_at` не старше 5 минут
(`Device::ONLINE_THRESHOLD_MINUTES`). Протухший heartbeat показывается как `inactive`.

## Публичный API

Базовый префикс — `/api/v1`. Три аудитории и три способа аутентификации.

### Привязка телефона (без ключа)

Кнопка «Подключить устройство» создаёт запись в `pairing_codes` (6 символов, живёт
5 минут, одноразовая) и рисует QR с JSON-полезной нагрузкой:

```json
{"pairing_code": "ABC123", "api_url": "https://panel.example.com"}
```

```http
POST /api/v1/devices/pair
{ "pairing_code": "ABC123", "device_name": "Samsung A54", "fcm_token": "...",
  "phone_number": "+99365123456" }
```

`phone_number` — номер SIM этого телефона, его вводит оператор: Android не даёт
прочитать собственный номер (`getLine1Number()` почти везде пуст). Необязателен,
можно заполнить позже в панели.

Код — сам по себе credential, поэтому эндпоинт открыт. Ответ `201` содержит
`device_token` (64 символа) — он показывается **один раз**, в БД лежит только его
sha256 (`devices.token_hash`). Просроченный, использованный или неизвестный код —
`404 invalid or expired code`.

### OTP (заголовок `X-Api-Key`)

```http
POST /api/v1/otp/send      { "phone": "+993XXXXXXXX", "from": "+993XXXXXXXX" }
POST /api/v1/otp/verify    { "otp_id": 42, "code": "123456" }
```

`from` необязателен: если у проекта несколько SIM, им можно зафиксировать
отправителя. Номер, которого нет ни у одного устройства проекта, — ошибка
вызывающего (`422 unknown sender number`), а не повод молча взять другой.
Ответ `202` называет номер, с которого уйдёт SMS.

* Формат номера: `+993` и ровно 8 цифр.
* Лимиты (`RateLimiter`): 1 запрос на номер в 60 секунд и 20 запросов на ключ в минуту.
  Оба лимита проверяются до того, как любой из них будет израсходован, — отказ по
  одному не съедает бюджет другого. Ответ `429` + `Retry-After`.
* `send` создаёт `otp_logs` в статусе `pending`, выбирает устройство проекта по
  round-robin (`status=active`, heartbeat не старше 5 минут, минимальный
  `last_dispatched_at`) и ставит в очередь `SendOtpViaFcmJob`. Ответ `202`.
* **Пропускная способность телефона.** У каждого устройства есть
  `throughput_per_minute` (по умолчанию 10, максимум 60). Телефон, выбравший
  свой лимит за последние 60 секунд, пропускается; если лимит выбрали все, ответ
  `429 all devices are at their throughput limit` с `Retry-After`. Очереди здесь
  сознательно нет: код живёт 5 минут, и SMS после его истечения хуже честного
  отказа. Лимит не выдуманный — одна отправка занимает 2–5 секунд, а Android
  режет фоновую рассылку примерно на 30 сообщениях за полчаса.
* Если живых устройств нет — `503 no active device available`, лог сразу `failed`.
  Rate limit при этом **не списывается**: пустой пул устройств — проблема шлюза,
  а не вызывающего, и он должен иметь возможность повторить запрос сразу.
* Если FCM не принял сообщение, `SendOtpViaFcmJob` передаёт OTP следующему
  устройству в round-robin и помечает лог `failed` только когда перебран весь пул.
### Статус кода

```http
GET /api/v1/otp/42     X-Api-Key
→ { "otp_id": 42, "status": "sent", "phone": "+993…", "from": "+993…",
    "attempts": 0, "attempts_left": 5, "created_at": "…", "expires_at": "…" }
```

Запасной путь к вебхукам: если приёмник лежал дольше, чем живут ретраи, судьбу
кода больше узнать неоткуда. Код в ответ не попадает ни в каком виде, а чужой
`otp_id` отвечает `404`, а не «нет доступа» — существование чужих
идентификаторов тоже не наше дело раскрывать.

### Идемпотентность (`Idempotency-Key`)

Необязательный заголовок на обоих `/otp/*`. Повтор запроса с тем же ключом
возвращает тот же ответ, ничего не выполняя заново:

```http
POST /api/v1/otp/send
X-Api-Key: sk_live_…
Idempotency-Key: order-42

→ 202 (первый раз)
→ 202 + Idempotent-Replay: true (повтор)
```

Это защита не от кривых клиентов, а от сети: таймаут у вызывающего ничего не
говорит о том, выполнился запрос или нет, и единственный безопасный ответ —
ретрай. Без идемпотентности он стоил бы второй SMS.

* Ключ уникален **в пределах API-ключа**: «order-42» двух разных клиентов не
  столкнутся.
* Тот же ключ с другим телом — `422`: почти всегда это ошибка на стороне
  клиента, и отвечать «как в прошлый раз» значило бы её проглотить.
* Пока первый запрос в полёте, дубль получает `409` + `Retry-After`.
* `429` и `5xx` **не запоминаются**: это «попробуйте позже», а не результат.
  Иначе клиент на сутки залип бы на собственном отказе.
* Записи живут 24 часа, чистит `idempotency:sweep-expired` (раз в час).

### Вебхуки

Без них интегратор узнаёт только, что запрос **принят в очередь** — ответ `202`
не означает, что SMS ушла. Адрес и секрет задаются в панели (вкладка
«Вебхуки»), события уходят POST-ом с JSON:

```json
{ "event": "otp.sent", "occurred_at": "…", "data": { "otp_id": 42, "status": "sent", "from": "+993…" } }
```

| Событие | Когда |
|---|---|
| `otp.sent` | телефон отдал SMS оператору |
| `otp.failed` | отправить не удалось |
| `otp.verified` | клиент ввёл правильный код |
| `otp.expired` | код истёк неподтверждённым |
| `webhook.test` | кнопка проверки в панели |

Подпись — HMAC-SHA256 от `timestamp.тело` в заголовке `X-Gateway-Signature`
(`t=<unix>,v1=<hex>`), как у Stripe. Метка времени обязательна: без неё
подписанный запрос можно записать и воспроизвести через месяц; получателю
следует отвергать всё старше 300 секунд. Код OTP в событие не попадает никогда.

Доставка — 5 попыток с паузами 10с → 15м, таймаут 10 секунд, успех — любой 2xx.
Каждая попытка пишется в `webhook_deliveries` и видна в панели: это ответ на
«нам ничего не приходило». События поднимаются наблюдателем на переходе статуса,
поэтому их одинаково видят и `verify`, и отчёт телефона, и failover, и
уборщик просрочек (он обновляет пачкой, поэтому события там поднимаются явно).

* `verify`: просрочка — `410 expired`, максимум 5 попыток (`otp_logs.attempts`),
  после чего лог навсегда `failed`. Успех переводит лог в `delivered` и повторно
  не срабатывает (`410 already verified`).

### Отчётность устройства (заголовок `X-Device-Token`)

```http
POST /api/v1/devices/heartbeat       { "fcm_token": "...", "battery_level": 87 }   // оба поля необязательные
POST /api/v1/devices/report-status   { "otp_id": 42, "status": "sent" | "failed" }
```

Устройство может отчитаться только по тем OTP, которые ему и были отправлены,
и не может перебить уже подтверждённый (`delivered`) лог.

`fcm_token` в heartbeat — лечение ротации push-адреса. Firebase меняет токен по
своему усмотрению, и без этого сервер продолжал бы слать команды в никуда, пока
кто-нибудь не заметит, что один телефон перестал отвечать. Телефон
переподтверждает адрес каждые 90 секунд, и привязка чинится сама.

## Хранение кода OTP

Два поля, потому что нужны две несовместимые вещи:

* `code_hash` — bcrypt, для `verify`. Не расшифровывается.
* `code_encrypted` — обратимое `encrypted`-поле (каст Eloquent), нужно ровно один раз,
  чтобы собрать текст SMS в `SendOtpViaFcmJob`. Сразу после отправки зануляется.

## Firebase

```dotenv
FIREBASE_CREDENTIALS_PATH=   # путь к service account json
FIREBASE_PROJECT_ID=
```

Команды уходят data-only сообщением с `priority: high` и TTL, равным времени
жизни кода (`OtpLog::LIFETIME_MINUTES`): обычный приоритет Android вправе
придержать до выхода из Doze — для OTP это равносильно недоставке, а SMS,
доставленная после истечения кода, только путает клиента и стоит денег.

Реальный проект не подключён. `App\Contracts\FcmSender` биндится на
`FirebaseFcmSender` (kreait/firebase-php), который создаёт SDK лениво — приложение
поднимается и без файла ключа, а неудачная доставка просто переводит лог в `failed`.
В тестах `Fcm::fake()` подменяет биндинг записывающей заглушкой:

```php
$fcm = Fcm::fake();
// ...
$fcm->assertSentTo('fcm-device-1', fn (array $data) => $data['type'] === 'send_sms');
$fcm->shouldFail(); // проверить ветку неуспешной доставки
```

## Продакшен: Postgres и Redis

SQLite здесь не «медленнее» — он просто не выдерживает того, что шлюзу нужно
делать постоянно: несколько воркеров `queue:work` пишут одновременно и вместо
записи получают `database is locked`. Поэтому в бою — Postgres, а очередь
уезжает в Redis, чтобы не конкурировать с приложением за те же блокировки.

### Поднять инфраструктуру

```bash
docker compose up -d          # postgres:16-alpine + redis:7-alpine
php artisan migrate --force
php artisan db:seed --force   # по желанию: демо-проект и ключ
```

Данные лежат в именованных томах и переживают пересоздание контейнеров.
Наружу порты открыты только на `127.0.0.1` — база не должна торчать в сеть.

**Порт 5432 занят.** Compose публикует Postgres на `55432`: на машинах
разработчиков стандартный порт часто держит нативный PostgreSQL, и контейнер
падает с невнятной ошибкой доступа к сокету. Если хотите использовать
установленный локально сервер вместо контейнера — поменяйте в `.env`
`DB_PORT=5432` и свои учётные данные, compose не нужен.

### .env

```dotenv
DB_CONNECTION=pgsql
DB_HOST=127.0.0.1
DB_PORT=55432
DB_DATABASE=otp_gateway
DB_USERNAME=otp
DB_PASSWORD=secret

REDIS_CLIENT=predis
REDIS_HOST=127.0.0.1
REDIS_PORT=6379

QUEUE_CONNECTION=redis
CACHE_STORE=redis
SESSION_DRIVER=redis
```

**Клиент Redis.** В PHP этой сборки нет расширения `phpredis`, поэтому нужен
composer-пакет:

```bash
composer require predis/predis
```

Пока пакет не установлен, держите `QUEUE_CONNECTION=database` — очередь будет
жить в Postgres. Это рабочий вариант: конкурентные воркеры Postgres выдерживает,
Redis снимает с него нагрузку, но не является обязательным.

### Воркер и планировщик

Без них шлюз не работает: отправка кодов и доставка вебхуков живут в очереди, а
уборки просрочек и проверка здоровья — в планировщике. Упавший воркер ничего не
сообщает, коды просто копятся и протухают.

Готовые конфиги — в `deploy/`:

```bash
sudo cp deploy/supervisor/otp-gateway.conf /etc/supervisor/conf.d/
sudo supervisorctl reread && sudo supervisorctl update
```

или systemd:

```bash
sudo cp deploy/systemd/otp-*.service /etc/systemd/system/
sudo systemctl enable --now otp-queue otp-scheduler
```

Планировщик равнозначно заменяется строкой в системном cron:

```cron
* * * * * cd /var/www/otp-gateway && php artisan schedule:run >> /dev/null 2>&1
```

На Windows supervisor нет: воркер и планировщик оформляются службами через
NSSM или заданиями в планировщике задач.

### Тесты на боевой СУБД

Обычный прогон идёт на sqlite `:memory:` — это быстро и годится для ежедневной
работы. Но различия с Postgres (строгий GROUP BY, поведение enum, регистр
идентификаторов) видно только на нём:

```bash
docker compose up -d
docker exec otp-postgres psql -U otp -d otp_gateway -c "CREATE DATABASE otp_gateway_test OWNER otp;"
vendor/bin/phpunit -c phpunit.pgsql.xml
```

## Алёрты

Шлюз ломается тихо: телефон ушёл в сон, воркер не поднялся после перезагрузки,
оператор начал резать SMS. Ни одно из этих состояний не бросает исключений — их
видно только по данным, и только если смотреть. Смотрит `gateway:check-health`
раз в минуту:

| Авария | Условие | Порог |
|---|---|---|
| `devices.offline` | у проекта есть телефоны, но ни один не на связи | `GATEWAY_ALERT_OFFLINE_MINUTES` (10 мин) |
| `otp.failure_rate` | доля `failed` за час выше порога | `GATEWAY_ALERT_FAILURE_RATE` (30%), не меньше `..._MINIMUM` (10) отправок |
| `queue.backlog` | готовая задача ждёт дольше порога | `GATEWAY_ALERT_QUEUE_MINUTES` (5 мин) |

* Письмо уходит **один раз** — на открытии аварии, и ещё одно на закрытии.
  Иначе при проверке раз в минуту владелец получал бы письмо в минуту.
* Уведомления идут **синхронно, мимо очереди**: одна из аварий — «очередь не
  разбирается», и сообщение о ней не должно ждать в той же очереди.
* Telegram (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) — необязательный канал,
  потому что почту ночью никто не читает. Упавший Telegram не роняет проверку.
* `expired` в долю ошибок не входит: код, который клиент просто не ввёл, — его
  решение, а не поломка шлюза.
* Очередь проверяется только у `database`-драйвера. Для redis мы внутрь не
  смотрим и не врём, что всё хорошо, — это работа внешнего мониторинга.

Открытые аварии видны на странице обзора проекта.

Планировщик держит проверку здоровья и три уборки:

* `otp:sweep-expired` — переводит `pending`/`sent` с истёкшим `expires_at` в
  `expired` и зануляет оставшиеся `code_encrypted`. Без неё логи вечно висят
  «в процессе», а счётчики врут.
* `devices:sweep-stale` — гасит `status` устройств, переставших слать heartbeat.
  На выбор устройства это не влияет (там фильтр по `last_seen_at`), но колонка
  перестаёт врать.
* `idempotency:sweep-expired` — раз в час убирает запомненные ответы старше
  суток вместе с номерами получателей в их телах.
