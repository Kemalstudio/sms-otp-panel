# OTP Gateway — Android-клиент

Телефон, который физически отправляет SMS по команде панели.

Панель генерирует код, кладёт задачу в очередь и шлёт data-push через FCM —
дальше всё делает это приложение: принимает команду, отправляет SMS через
`SmsManager` и отчитывается о результате. Без него шлюз нерабочий: некому слать
heartbeat, и через 5 минут после привязки все `POST /api/v1/otp/send` начнут
отдавать `503 no active device available`.

## Что умеет

| Часть | Файл |
|---|---|
| Привязка по QR / вручную, ввод номера SIM | `ui/GatewayViewModel.kt`, `ui/PairingScreen.kt` |
| Хранение токена | `data/DeviceStore.kt` (EncryptedSharedPreferences) |
| HTTP к шлюзу | `data/GatewayClient.kt` |
| Приём push и отправка SMS | `sms/GatewayMessagingService.kt`, `sms/OtpDelivery.kt`, `sms/SmsSender.kt` |
| Heartbeat, заряд, самолечение FCM-токена | `service/HeartbeatService.kt`, `data/BatteryGauge.kt` |
| Журнал отправок и статистика | `data/SmsLogStore.kt`, `ui/LogScreen.kt` |
| Повтор недоставленных статусов | `service/ReportRetryWorker.kt` |
| Уведомления о сбоях | `service/Alerts.kt` |
| Выбор SIM, тестовое SMS, настройки | `data/SimCatalog.kt`, `ui/SettingsScreen.kt` |
| Живучесть | `service/BootReceiver.kt`, `service/WatchdogWorker.kt` |

Экранов три (нижняя навигация):

* **Обзор** — состояние связи с пульсирующим индикатором, счётчики за сутки
  (отправлено / ошибок / успешность), красные карточки по всему, что молча
  ломает доставку, последние 5 отправок, данные устройства.
* **Журнал** — все отправки с фильтром «все / отправлены / ошибки», причиной
  ошибки и пометкой «статус не доставлен».
* **Настройки** — SIM для отправки, тестовое SMS, уведомления о сбоях,
  чек-лист готовности телефона, досылка статусов, отвязка.

## Сборка

Нужен `google-services.json` из того же Firebase-проекта, чей service account
прописан на сервере в `FIREBASE_CREDENTIALS_PATH`:

```
app/google-services.json
```

Затем:

```bash
./gradlew :app:assembleDebug
```

Плагин `com.google.gms.google-services` подключается только если файл на месте —
без него проект компилируется (удобно для CI), но привязка блокируется с явным
сообщением: push работать не будет. Это видно через
`BuildConfig.HAS_FIREBASE_CONFIG`.

### Про репозитории

`repo1.maven.org` доступен не из всякой сети, поэтому в `settings.gradle.kts`
первым идёт зеркало Maven Central на Google Cloud Storage, а канонический хост
оставлен запасным. Артефакты там идентичные.

## Привязка устройства

1. В панели: проект → **Устройства** → **Подключить устройство**.
2. В приложении — **Сканировать QR-код**. Код живёт 5 минут и срабатывает один раз.
3. Если камеры или Play Services нет — **Ввести код вручную**: адрес сервера и
   6-значный код.

При привязке приложение спрашивает **номер этой SIM**. Прочитать его само оно не
может: `getLine1Number()` почти на всех прошивках и у всех операторов возвращает
пустую строку, а с Android 11 требует привилегий оператора связи. Номер нужен,
чтобы панель показывала, с какого номера уходят коды, и чтобы вызывающий мог
зафиксировать отправителя параметром `from`. Поле необязательное — его можно
заполнить позже в панели.

Сервер отдаёт `device_token` **ровно один раз**. Он ложится в
EncryptedSharedPreferences и исключён из облачного бэкапа
(`res/xml/data_extraction_rules.xml`) — токен не должен переезжать на другой
аппарат. Потеряли — нужна новая привязка.

## Что обязательно выдать на телефоне

Приложение само показывает это карточками на главном экране и чек-листом в
настройках:

* **Разрешение SEND_SMS** — без него телефон принимает команды, но не может
  отправить код.
* **Снятие ограничений батареи** — иначе OEM-менеджер (особенно Xiaomi, Huawei,
  Samsung) замораживает foreground-службу, heartbeat перестаёт уходить, и шлюз
  тихо убирает телефон из пула.
* **Уведомления** — без них не будет видно, что связь потеряна или SMS не ушла.
* `READ_PHONE_STATE` — необязательное, только чтобы показать названия SIM.
  Без него отправка идёт с карты по умолчанию.

Плюс здравый смысл: аппарат на зарядке, активная SIM с балансом.

## Почему heartbeat — foreground-служба

Сервер считает устройство живым, если `last_seen_at` не старше 5 минут.
Минимальный период у WorkManager — 15 минут, втрое больше окна. Поэтому
heartbeat живёт в foreground-службе с интервалом 90 секунд (и 20 секунд на
повтор после сбоя), а WorkManager оставлен сторожем: раз в 15 минут поднимает
службу, если её всё-таки убили.

Тип службы — `specialUse`, а не `dataSync`: у последнего на Android 15 есть
суточный лимит в 6 часов, что для круглосуточного шлюза не годится.

Три подряд неудачных heartbeat (~1 минута) поднимают громкое уведомление:
панель в этот момент уже уводит заказы на другие устройства, и оператор должен
узнать об этом раньше, чем клиент.

## Надёжность доставки

Слабое место любого SMS-шлюза — не отправка, а **отчёт** о ней: SMS ушла, сеть
пропала, панель до сих пор считает код `pending`, сервер через 5 минут пометит
его `expired`, хотя клиент код получил.

Поэтому каждая отправка сразу пишется в локальный журнал (`data/sms-log.json`,
последние 500 записей) с флагом `reported`. Если `POST /devices/report-status`
не прошёл, запись остаётся в очереди, и `ReportRetryWorker` досылает её с
экспоненциальной паузой. Очередь разбирается при возврате связи, при
перезапуске процесса, по сторожевому таймеру и по кнопке «Дослать статусы».
`404` от сервера снимает запись из очереди — такого лога у устройства нет, и
повторять бессмысленно.

Сама отправка идёт под partial wake lock с таймаутом 25 секунд: процесс после
`onMessageReceived` может быть заморожен, а зависший радиомодуль не должен
утащить с собой весь обработчик push.

## Контракт с сервером

```http
POST /api/v1/devices/pair
{ "pairing_code": "ABC123", "device_name": "Samsung A54", "fcm_token": "...",
  "phone_number": "+99365123456" }
→ { "device_id": 7, "device_token": "<64 символа, один раз>" }

POST /api/v1/devices/heartbeat          X-Device-Token
{ "fcm_token": "<текущий адрес push>", "battery_level": 87 }
→ { "device_id": 7, "status": "active", "throughput_per_minute": 10 }

POST /api/v1/devices/report-status      X-Device-Token
{ "otp_id": 42, "status": "sent" | "failed" }
```

Входящий push (data-only):

```json
{ "type": "send_sms", "otp_id": "42", "phone": "+99365123456", "message": "Ваш код: 123456" }
```

`status` отправляется по фактическому результату из `PendingIntent` метода
`sendTextMessage`, а не по «не бросило исключение» — иначе шлюз считал бы
доставленным всё, что ушло в выключенный радиомодуль. Длинное сообщение
считается отправленным только когда приняты **все** его части.

Заряд приезжает вместе с heartbeat: стойку из телефонов надо видеть целиком, а
разряжающийся аппарат выпадет из пула через несколько часов. Оттуда же телефон
узнаёт свой лимит скорости — он задаётся в панели, а не хранится на устройстве.

`fcm_token` в heartbeat — лечение ротации токена: Firebase меняет адрес по
своему усмотрению, и раньше сервер продолжал слать push в никуда. Теперь телефон
переподтверждает адрес каждые 90 секунд, и привязка чинится сама.

## Известные ограничения

* **Нет отчёта о доставке сети.** Отслеживается только `sentIntent`
  («радиомодуль принял»), не `deliveryIntent`.
* **Журнал только локальный.** Очистка журнала на телефоне убирает и
  недоставленные статусы — панель о них уже не узнает.
* **Нет тестов.** Инструментальные тесты потребовали бы эмулятора с телефонией.
